# Deploy — 2 November 2026

Five changes: three bug fixes to how a visit ends, two new capabilities
(forgiving a charge, correcting a test), and a correction to the day's money
figures. Two migrations.

Most of this file is reusable. When there is a second deploy runbook, lift the
general parts into `deploying.md` and leave only the specifics here.

## Before

**1. Run the gate.** It is the whole contract; nothing below substitutes for it.

```bash
pnpm verify
```

Read the exit code, not the last lines of output. Piping through `tail` reports
_tail's_ status — that masked six real test failures on 30 Oct and again on
2 Nov. If running it in the background, append your own marker:

```bash
pnpm verify > verify.log 2>&1; echo "EXIT=$?" >> verify.log
```

**2. Back up the database.** More than usual: `20261102130000` rewrites
`role.permissions` in place, and there is no tested restore (see the 30 Oct gap
audit).

```bash
pg_dump -Fc -d healthcloud -f ~/healthcloud-pre-2nov.dump
ls -lh ~/healthcloud-pre-2nov.dump    # must not be 0 bytes
```

**3. Merge and push.**

## Deploy

**4. Migrations BEFORE the application.**

```bash
pnpm --filter @healthcloud/db migrate:deploy
```

Expect exactly two:

```
20261102120000_a_charge_can_be_forgiven     — new invoice_write_off table
20261102130000_who_may_forgive_a_charge     — grants invoice:waive to 3 roles
```

**This order is not optional.** The invoice view now returns `writeOffs`, so an
application deployed before its table exists returns a 500 on _every_ invoice
read — the payment dialog, the finance page, and the board's money column. Both
migrations are safe to apply early: old code does not know the table, and an
extra permission is inert until there is a screen that uses it.

**Keep the output.** The second migration prints:

```
NOTICE: Gave invoice:waive to N role(s); left M customised one(s) as they were.
```

**5. Deploy API and web.**

## After

**6. If `M` was not zero**, those roles had been edited in this clinic and were
deliberately left alone — the migration only touches a role holding _exactly_
its shipped permission set, so it never overrules a choice an administrator
made. Add `invoice:waive` to them by hand in role management, or press reset on
the role. Then confirm:

```sql
SELECT key, 'invoice:waive' = ANY(permissions) AS can_waive
  FROM role WHERE key IN ('doctor','front_desk','finance');
```

All three should be `true`. The administrator already held it.

**7. Everyone signs out and back in.** Permissions travel in the signed access
token, so anyone logged in through the deploy keeps their old one until it
refreshes. The first support call will be a doctor saying the button is not
there; this is the answer.

**8. Smoke checks.** The three in bold had not been exercised in a browser at
the time of deploy.

| Where                            | Expect                                                       |
| -------------------------------- | ------------------------------------------------------------ |
| Board, previous day              | Close visit on a finished row; Did not come on a waiting one |
| Board, a test at a department    | Edit/Cancel test opens the dialog                            |
| A paid bill → patient → Payments | **Make this free** — money returns, bill reads Waived        |
| The same bill afterwards         | **Undo** puts the charge back as owing                       |
| Reports → Finance                | **"Made free"** carries a figure                             |
| Board header, after a waiver     | `collected` does NOT move; `made free` does                  |

**9. In the logs,** `ORDER_SETTLED`, `WRITE_OFF_EXCEEDS_CHARGE` and
`ORDER_NOT_PENDING` are refusals working correctly, not faults.

## Reading the day's money line

```
₹1,500.00 collected of ₹3,500.00 · ₹900.00 refunded · ₹400.00 made free · ₹500.00 due
```

**`collected − refunded` is what should be in the till.** It is counted from
payment rows, so it can be checked against a physical count — which is the whole
reason it stopped being derived.

The parts do **not** sum to `billed`, and the line does not claim they do. Three
things legitimately sit outside them:

- a DEFERRED bill — billed, not collected, not forgiven, and excluded from `due`
  because deferral counts as settled;
- any invoice waived **before this deploy**, which carries status `WAIVED` with
  no `invoice_write_off` row behind it. That describes every existing waiver in
  production, so past days will not balance and that is expected;
- seeded or hand-edited data with a status set directly and no payment rows.

Per-patient, the Amount column carries the same two figures where they apply, so
a number in the header can be traced to the rows behind it.

## The rollback boundary

**Rolling the application back is safe only until the first waiver is
recorded.**

After that, the old code's `totals()` does not subtract `writtenOffPaise`, so
every forgiven bill reads as owing again and the desk starts chasing patients
who were told the visit was free. Rolling the _migration_ back is worse: it
drops the table with the waivers inside it.

Past that point, fix forward.

## Known limitations, shipped knowingly

- **A row with more than one pending test only edits the first.** The board's
  quiet button hangs off a single `pendingOrderId`, so a second test is
  unreachable until the first is dealt with — and the billed/unbilled behaviour
  follows that first test. Found during testing on 2 Nov; not fixed.
- **`updateOrder` takes no invoice lock.** Two simultaneous edits of one order
  both try to replace the charge; the second fails cleanly on a missing line
  and rolls back, so it errors rather than duplicating. Matches `declineOrder`,
  which does not lock either. Untested under concurrency.
- **Forgiving a paid charge issues a refund**, so doctor, front desk and finance
  can now cause money to leave the till without holding `payment:refund`. That
  reverses FR-FIN-01 (clinic demos, 3 Sep 2026), knowingly and on the record:
  waivers are uncapped, and the control is visibility — who, how much, why,
  undeletable, totalled as "Made free" — rather than prevention.
- **Past days will not balance**, and neither will any patient waived before
  this deploy: those invoices carry status `WAIVED` with no write-off row, so
  the forgiveness is invisible to the new figure. Only waivers made from now on
  appear in "made free".
- **A part-forgiven bill reads `PARTIALLY_PAID`** although nobody paid. Status
  tracks how much is _settled_, and forgiven money settles as cash does.
  `paidPaise` stays zero and `writtenOffPaise` carries the amount, so the
  finance report still separates takings from giveaways.

## Unrelated: `apps/web/next-env.d.ts`

It will show as modified and block `git checkout`. It is generated, and its
third line names whichever dist directory Next ran with last — `.next-dev` after
`pnpm dev`, `.next-build` after `pnpm build` — so it flips every time you switch
between running the app and running the gate.

Discarding it is always safe: `git checkout -- apps/web/next-env.d.ts`.

Do **not** gitignore it without thinking: `apps/web/tsconfig.json` names it in
`include`, and it is what pulls in Next's global types. Untracked, a fresh clone
followed straight by `pnpm typecheck` fails on Next globals until somebody runs
`dev` or `build` once. Narveer's decision on 2 Nov 2026 was to leave it alone.
