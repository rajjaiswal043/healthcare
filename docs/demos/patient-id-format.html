Patient ID Format

Every hospital wants its own patient numbers — DRVIV-0001, and up from there. Almost all of this is already built; what is missing is being asked the question.

From clinic demos, 3 Sep 2026 4 requirements 5 decisions outstanding Mostly a screen, not a build

Read this before scoping it

Every patient already has a unique per-clinic ID. It is called the UHID, it appears on the record, on bills and in search, and it cannot be changed after registration. The clinic table already carries the format, and numbers are allocated by a database function that increments and returns in one statement — so two receptionists registering at the same moment can never be handed the same ID. That part is solved and should not be touched.

What that means concretely

Dr Vivek's clinic onboarded today gets DRV000001, not DRVIV-0001. Right mechanism, wrong prefix, wrong number of digits — and nobody was asked.

Requirements

FR-UID-01

Choose the format when the clinic is onboarded

Extends existing

Whoever onboards a clinic asks what the hospital wants its patient IDs to look like, and sets it there and then.

  • Prefix — the letters in front, including any separator the clinic wants. DRVIV- is a prefix; so is SNC/.
  • Number width — how many digits, zero-padded. Four gives 0001.
  • A live preview, updating as they type: “Your first patient will be DRVIV-0001.” This is the whole point of the screen — somebody choosing a format they cannot see will choose wrong.
  • Sensible defaults, so an onboarding that skips this still works, as it does today.
For the developer

The API already takes the prefix; it needs the digit width alongside it, and the onboarding screen needs both fields. The allocation function already composes the two correctly and needs no change.

FR-UID-02

The clinic can see its own format

New build

The format appears in the clinic's own settings, so an administrator can answer “what do our patient numbers look like?” without asking us. Shows the prefix, the width, an example, and how many IDs have been issued. Read-only for the clinic — changing it is the platform's job, for the reason below.

FR-UID-03

Changing the format after patients exist

New build

A clinic will ask for this, usually a fortnight in, usually because they got it wrong at onboarding.

Not negotiable

Existing patients keep the ID they were given. A UHID is printed on cards, written on files, quoted on bills and stuck on X-ray envelopes. Renumbering makes every one of those wrong, and the patient holding the card becomes untraceable.

  • Applies to patients registered from that moment on, never retrospectively.
  • Leaves the clinic with two formats in circulation, permanently. That is correct, and must not be tidied away.
  • Does not reset the counter. If 40 patients exist, the next is 41 in the new format. Restarting at 1 creates two patients whose numbers differ only by prefix — the one thing this ID exists to prevent.
  • Done by the platform, not the clinic, and recorded.

Say it on the screen when somebody changes it: “Patients already registered keep their existing IDs. This applies to new registrations only.”

FR-UID-04

Where the ID has to appear

Mostly done

Already true in most places; listed so nothing is missed once the format becomes something a clinic chose rather than something it was given.

  • The patient record and search results — searching by ID already works.
  • Every bill and receipt.
  • The prescription.
  • Diagnostic reports, including walk-in ones.
  • The patient's card, if the clinic prints one.

Decisions still needed

1. A template like DRVIV-{0000}, or two fields?

You described a template string. Two fields — prefix and digit width — produce exactly the same result, and that is what the database already stores.

Recommendation Two fields with a live preview. A template syntax invites the next question immediately — {YYYY} for the year, {DEPT} for the department, a check digit — and each one is a parser, a validator, and a new way for a clinic to lock itself into a format that collides with itself. Two fields cannot express anything that breaks. If you want the template box because it demos better, it can be a box that accepts one placeholder — but that is a presentation choice, not a capability.

2. Eight characters — is that enough prefix?

DRVIV- fits. DRVIVEKCLINIC- does not. Widening it is a small migration, but it must be decided before clinics start using it — narrowing it again later is not possible without touching issued IDs.

3. Can a clinic administrator change it themselves?

Recommendation No — platform only. It is a decision with permanent consequences that looks like a harmless setting, and there is no undo. A clinic that wants it changed should have to say so out loud to somebody.

4. Does the number ever restart — per year, say?

Recommendation No. DRVIV-2026-0001 and DRVIV-2027-0001 are two different patients whose IDs differ by a year nobody says out loud on the phone. If a clinic asks for it, that is decision 1 all over again.

5. Does a sequential number tell people too much?

DRVIV-0007 on a card says the clinic has seen seven patients. Patients compare cards, and so do competitors. Most Indian clinics number sequentially and nobody minds — but if it matters to any of your clinics, decide before the first card is printed, because the fix is a different numbering scheme entirely.

Honest summary

Scope, plainly

This is a screen, one database column exposed, and a preview. The identifier, its uniqueness, its atomic allocation, its per-clinic isolation and its appearance across the system are all built and working. Do not rebuild any of it — in particular, do not replace the allocation function. The whole requirement is: ask the question at onboarding, store the answer, show what it will look like, and be honest on screen about what changing it later does and does not do.
